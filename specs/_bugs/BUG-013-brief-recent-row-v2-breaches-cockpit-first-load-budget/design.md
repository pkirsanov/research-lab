# Design: BUG-013 — Analysis Of The First-Load Budget Breach

**Status:** Analysis complete. Remedy deliberately not selected.
**Workflow mode:** `bugfix-fastlane`
**Filed at commit:** `9af68427b`

---

## What This Document Does And Does Not Do

It establishes the mechanism, isolates the contributing change, quantifies the trajectory, and lays
out the four candidate remedies with their costs.

It does **not** select a remedy. The choice is between two intentions that are both documented and
both deliberate, and it belongs to Feature 026's owner. A filing task that picked one would prejudge
a product tradeoff under cover of a bug fix.

---

## Mechanism

`scripts/validate-tool-experience.mjs` builds a `briefFirstLoad` inventory by summing the byte
lengths of seven paths, and asserts the total is within `briefFirstLoadMaxBytes`:

```js
const firstLoadBytes = firstLoadPaths.reduce((total, path) => total + readRequired(path).length, 0);
...
{ artifact: 'brief-first-load', bytes: byteInventory.briefFirstLoad, budget: budgets.briefFirstLoadMaxBytes }
...
invariant(check.bytes <= check.budget, `${check.artifact} exceeds configured artifact byte budget`);
```

The total is 209,387. The budget is 204,800. The invariant fails, and fifteen selftest assertions
that depend on a green first-load inventory fail with it.

---

## Isolating The Contribution

Between `0f61d1a14` (197,756, green) and `9af68427b` (209,387, red), `brief-history.recent.jsonl`
supplied 10,848 of the 11,631 added bytes — **93%**. The other six files added 783 bytes combined,
which is ordinary content drift and is not the defect.

The recent artifact held **30 rows at both commits**. Row count is not the variable.

Split the file by contract and the variable is obvious:

| row class | count at `9af68427b` | mean bytes | ratio |
|---|---:|---:|---:|
| without `tracked` (pre-v2 source rows) | 28 | 397 | 1.0x |
| with `tracked` (v2) | 2 | 4,939 | **12.4x** |

Composition of the largest v2 row, 4,947 bytes:

| key | bytes | note |
|---|---:|---|
| `tracked` | 3,565 | 12 instruments, ~297 bytes each |
| `crossAsset` | 613 | |
| `dark` | 325 | |
| `claims` | 61 | |
| everything else (all of v1) | ~383 | matches the 397-byte v1 row mean |

The four keys added by the `brief-history-recent-row/v2` bump account for 4,564 of 4,947 bytes,
which is **92% of a v2 row**. `tracked` alone is 72%.

## Why The Red Appeared On A Commit That Changed No Source

The enabling code change is Feature 026 Scope 3, commit `3855ee75d`, which raised `compactRow()` to
`brief-history-recent-row/v2` and added the four keys. It is an ancestor of `9af68427b` and a
descendant of `0f61d1a14`, so it sits inside the measurement window.

The bytes did not appear at that commit. `brief-history.recent.jsonl` is regenerated by
`scripts/shard-brief-history.mjs`, and `compactRow()` can only emit a v2 key when the source row
carries it. Historic source rows carry none, so they project as `null` at almost zero cost. Only
runs executed **after** the contract bump produce a full-price row.

The growth therefore materialised through scheduled cron refreshes, and the commit that crossed the
budget is a cron commit rather than a source commit. That is a delivery-latency effect, not an
absence of cause. Stating it as "no code changed" would be wrong and would misdirect the remedy
toward the cron.

The distinction matters for one reason: **the cause is still arriving.** Two of thirty rows have
been repriced. Twenty-eight have not.

---

## Trajectory

Every cron run replaces the oldest row with a v2 row. The v2 population only rises, and terminates
at 30.

```
steady state file  = 30 x 4,947            = 148,410 bytes  (~145 KB)
other six files    = 209,387 - 21,006      = 188,381 bytes
steady state total = 188,381 + 148,410     = 336,791 bytes  (~329 KB)
budget                                     = 204,800 bytes  (200 KB)
overage                                    = 1.64x
```

Two consequences follow.

**The current 4,587-byte overage understates the problem by roughly 29x.** The eventual overage is
131,991 bytes.

**A single file of seven ends up at 72% of the whole payload budget.** That is the same fraction
`tracked` occupies inside a row, which is not a coincidence: the per-instrument payload dominates at
both scales.

---

## The Design Conflict

Both positions are recorded in the doc comment above `compactRow()` in
`scripts/shard-brief-history.mjs`.

**Position A, the artifact's founding contract.**

> The compact projection the cockpit can afford to load every time. Deliberately excludes
> toolReads / toolCoverage / groups / sectors / names: those are the monthly shard's job, and a page
> that needs them should read the one month it cares about.

The word "afford" is doing the work. This artifact was created by the sharding change specifically
because `brief-history.jsonl` had reached 2.37 MB and the page fetched all of it on every load. The
exclusion list names per-instrument and per-group content, and gives the reason: that content
belongs in the monthly shard, which a page fetches only when it needs it.

**Position B, Feature 026 Scope 3's rationale.**

> The four new keys carry what the run SAW, which is what makes "what changed since I last told you"
> answerable without refetching a single instrument.

Also deliberate, also reasoned, and it names a real property. Answering "what changed" from the
first-load payload alone means no second request and no per-instrument refetch.

**Where they collide.** `tracked` is per-instrument data — the same class Position A excludes by
name. Position B needs it present in `recent` precisely because that is the file already loaded.
Position A needs it absent from `recent` precisely because per-instrument data is what made the
predecessor unaffordable.

At the current encoding, both cannot hold. The measurement says so: 3,565 bytes of per-instrument
content per row, 30 rows, in a file that is one of seven inside a 200 KB budget.

**This packet resolves nothing here.** Both authors wrote down why. Neither reason has been shown
wrong. Selecting between them trades a product property against a page-weight budget, which is
Feature 026's owner's call.

---

## Why The Existing Bounds Did Not Contain This

`tool-experience.config.json` declares three relevant budgets:

```
"briefHistoryRecentMaxBytes": 204800,
"briefHistoryRecentMaxRows": 30,
"briefFirstLoadMaxBytes": 204800
```

**The row cap held and was irrelevant.** 30 rows before, 30 rows after. It bounds a dimension that
did not move. A retention policy expressed in rows cannot see a 12.4x change in the price of a row.

**The per-file byte budget is structurally non-binding.** `briefHistoryRecentMaxBytes` equals
`briefFirstLoadMaxBytes` exactly. One of seven files is permitted to consume the entire allowance of
the whole payload by itself. Concretely: at the projected steady state of 148,410 bytes this file is
**still inside** its own 204,800 per-file budget while putting the aggregate 1.64x over. The
per-file check cannot fire before the aggregate check does, in any scenario, so it contributes no
detection the aggregate does not already provide.

That is the gap FR-013-003 names. The artifact needs a byte bound that binds.

## Candidate Remedies

Enumerated with costs. **No preference ordering is expressed or implied.**

### 1. Move `tracked` to the monthly shard

Applies Position A literally. `tracked` is per-instrument content, the exclusion list names
per-instrument content, so it goes where the exclusion says.

*Effect on bytes.* Removes ~3,565 of ~4,947 per row. A v2 row falls to ~1,382 bytes; 30 rows reach
~41,460; the payload lands near 229,841, still over. **This alone does not reach green** unless
`crossAsset` also moves or the other six files shrink. Worth stating plainly, because the intuitive
reading is that removing 72% of the row fixes it.

*Cost.* Directly removes the property Position B was built to deliver. Answering "what changed"
requires a monthly-shard fetch — the exact refetch Scope 3 set out to eliminate.

*Contract impact.* Not additive. Requires a `contractVersion` change and a consumer audit.

### 2. Keep `tracked` in `recent`, encode it compactly

Keeps both positions by attacking the encoding rather than the content.

*Signal.* 3,565 bytes for twelve instruments is ~297 bytes each. For per-instrument state that
looks reducible: repeated key names across twelve objects, full-precision floats, and possibly null
fields that could be omitted.

*What is unknown.* No measurement in this packet decomposes those 297 bytes into structural content
versus encoding overhead. Whether a compact encoding reaches the budget is **unestablished**, and
FR-013-002 requires clearing the projection, not today's number. Reaching ~145 KB down to a share
that fits alongside 188,381 bytes of other files means roughly a 4x reduction, which is a strong
demand for an encoding change alone.

*Cost.* Readability of the artifact. A positional or dictionary-compressed encoding is harder to
inspect by eye, and this file is currently trivially greppable.

### 3. Reduce the recent window for v2 rows

Keeps the keys and the encoding, shortens history.

*Effect on bytes.* Linear and predictable. At 4,947 bytes per row, the file's contribution is
`4,947 x N`. Fitting inside `204,800 - 188,381 = 16,419` bytes allows **N = 3**. Three rows is not
a trend view. Combining this with remedy 2 is the only way it yields a usable window.

*Cost.* Trend depth, which is the artifact's purpose. Interacts with
`briefHistoryRecentMaxRows` and with any consumer assuming 30 rows.

### 4. Raise `briefFirstLoadMaxBytes`

**Recorded for completeness and refuted by the projection.**

Raising the budget to clear 209,387 satisfies FR-013-001 and fails FR-013-002 as soon as the window
turns over. The number that clears the projection is ~336,791, which does not "raise a budget" — it
declares a 329 KB unconditional first-load payload acceptable. That is a different decision, on
different grounds, and it should be argued on page-weight terms rather than adopted as the path of
least resistance during a red build.

It is listed because an owner is entitled to make it knowingly. It must not be made accidentally.

---

## The Check Itself Is Correct

`validate-tool-experience.mjs` detected genuine unbudgeted growth in a payload every visitor
downloads, and detected it while 28 of 30 rows were still unrepriced. The remedy is cheap now
precisely because the guard fired early.

No remedy in this packet weakens it. FR-013-005 forbids that explicitly.

## Open Questions For The Owner

1. Which of Position A and Position B yields, and what is the recorded reason?
2. If `tracked` stays in `recent`, what per-instrument byte cost is acceptable, and is that
   reachable by encoding alone?
3. Should `crossAsset` (613 bytes/row, ~18,390 at 30 rows) be evaluated on the same criterion, or is
   it small enough to keep unconditionally?
4. What byte bound should the recent artifact carry so it binds before the aggregate does? A value
   equal to the aggregate budget cannot.
5. Does the answer generalise? If a future scope adds a fifth key on Position B's reasoning, does
   the same conflict recur, and is a standing rule needed rather than a one-time adjudication?
